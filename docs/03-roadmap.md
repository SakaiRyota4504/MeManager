# 実装ロードマップ

スケジュール管理を動く状態まで持っていくための進め方。
各ステップは「終わった時点で何かが動く」ように区切る。

## 方針

- **ウェブを先に完成させ、デスクトップは後から包む。**
  デスクトップを先に作ると、両方を同時にデバッグすることになり進まない。
- **画面より先にデータ構造を固める。**
  担当者必須・繰り返し・インポートはすべてデータ構造に依存する。
- **外部データの取込は後回しにしない。**
  手入力で数十件を登録する状況が続くと、そもそも使われなくなる。
- **取込は1本にする。**
  外部サービスごとに取込口を作らない。CSV と .ics を読める口を1つ作り、
  データ源の違いは「CSV を作る側」で吸収する。
- **取込の頻度は月1回＋年1回。** 自動化は作らない。
  そのぶん「毎月の繰り返し操作を短くする」ことに手をかける。
- **塊で入れて、塊で消す。** 取り込みと一括削除は対で作る。
  差分更新は作らない。入れ直したいときは消して入れ直す。

## ステップ

### Step 0: 土台づくり

- Next.js プロジェクトの作成、TypeScript / Lint / フォーマッタの設定
- Supabase プロジェクトの作成、ローカル開発環境（Supabase CLI）
- Vercel へのデプロイと、環境変数の設定
- リポジトリの CI（型チェックと Lint）

**完了の目安**: 空の画面が本番URLで表示され、Supabase に接続できる。

### Step 1: 認証と家族・メンバー

対応する要件: FR-A01〜A15

- Supabase Auth によるログイン・ログアウト
- `families` / `members` / `calendars` テーブルとマイグレーション
- 最初の1人のログイン時に、家族と「家族共有」カレンダーを自動作成
- **アプリにサインアップ画面を置かない。**アカウントを用意するのは管理者だけ
  （公開サインアップも止める）
- メンバーの登録（表示名だけ／ログイン付き／メールアドレスだけ）、
  あとからログインを設定
- メンバーの削除と復帰、表示名の変更
- **RLS ポリシーをこの段階で入れる**（後付けにすると全テーブルの見直しになる）

**完了の目安**: 2つのアカウントが同じ家族に属し、別の家族のデータが見えない。
管理者が登録していない人はアカウントを作れず、
外したメンバーからはデータが見えなくなる。
色の設定は Step 4 以降に回す（今は8色から自動で割り当てる）。

### Step 2: 予定の基本機能

対応する要件: FR-E01〜E11、FR-M01〜M04、FR-V01〜V07、FR-V09
画面の作りは要件定義9章（試作で確認済み）に従う。

- `events` / `event_assignees` テーブル
- 予定の作成・編集・削除（担当者必須のバリデーションを含む）
- 月表示・リスト表示
- 予定の詳細表示
- 担当者の色分け表示

**画面は [docs/prototypes/calendar.html](prototypes/calendar.html) をなぞる。**
配色・文字サイズ・画面幅ごとの作り分けは試作で実測して決めてあるので、
そこから作り直さない。

**完了の目安**: 予定を登録して月表示に出せる。担当者なしでは保存できない。

### Step 2.5: 画面の骨組みとURLの整理（実装済み）

対応する設計: [06-app-shell.md](06-app-shell.md)

スケジュール管理は4機能のうちの1つでしかない。
機能が増えたときのメニューの置き場を、ここで決めて作っておく。

- 機能の一覧（`src/lib/nav/features.ts`）と、それを読むシェル
- URL の整理（`/calendar` → `/schedule`、`/members` → `/settings/members`）
- 機能の中の画面を並べる2段目のタブ（1つしか無い機能では出さない）

**メニューは機能が2つになるまで表に出さない。**
行き先が1つしか無いのにタブを出しても意味がない。
ここで作るのは「足せば出る」状態までで、見た目はほとんど変わらない。

**URL を変えるのはこの時点でやる。** 使い始めてからだと、
ブックマークや家族に伝えたURLが変わって面倒になる。

**完了の目安**: 機能を1つ足す作業が「配列に1行足す」で済む状態になる。

### Step 3: 絞り込み（実装済み）

対応する要件: FR-M05〜M09、FR-M11、FR-V10、NFR-P02

- メンバー単位の表示切替
- 「自分の予定のみ」の切替（ボタンと `M` キー）
- 絞り込み状態の保存（`user_preferences`）と URL への反映
- 絞り込み中であることの明示
- 週の開始曜日の設定（FR-V10）

**カレンダー単位の絞り込み（FR-M10）は作らない。**
カレンダーは「家族共有」1つに固定したので、絞る対象がない。

**完了の目安**: 受け入れ基準 AC-06〜AC-08 を満たす。

### Step 4: 週表示と操作性（実装済み）

対応する要件: FR-V02、FR-V03、FR-E07、9.3 節

- 週表示・日表示（縦が時刻、横が日）
- 週表示・日表示で、空いているところをなぞって作成
- キーボードショートカット（← → T N M 1〜4）
- スマートフォン幅のレイアウト調整（操作の行を2段に畳む）

**見せ方と日付は URL に持たせる**（`?view=week&date=2026-09-21`）。
「この週を見て」と家族にリンクを送れるようにするため。

**完了の目安**: 予定の追加が10秒以内に終わる。画面幅375pxで操作できる。

### Step 5: 繰り返し予定（実装済み）

対応する要件: FR-R01〜R03、FR-R05〜R08

- `events.rrule` 列と `event_exceptions` テーブル
- 繰り返し設定の入力UI（毎日／毎週／毎月／毎年、間隔、終わり方）
- サーバー側での展開（予定を取るところで開く）
- 「この回のみ / これ以降 / すべて」の編集・削除

**展開ロジックは予定に結び付けていない。**
`src/lib/recurrence/` は「ルールと期間を渡すと**日付の一覧**が返る」だけで、
予定のことを何も知らない。
日付を予定の形に当てはめるのは `src/lib/calendar/series.ts` の仕事。
将来の習慣管理では前者をそのまま使う
（[00-product-vision.md](00-product-vision.md) 4.4）。

展開は RFC 5545 のライブラリ（`rrule`）に任せ、自前で書かない。
毎月31日の扱いのような細かい決まりを自前で持ちたくないため。

**第N曜日（FR-R04・Could）は作っていない。**
「毎月第2土曜」は年に12回しかなく、必要になってからでよい。

**完了の目安**: 受け入れ基準 AC-09 を満たす。

### Step 6: CSV 取込と一括削除（実装済み）

対応する要件: FR-I01、FR-I04、FR-I10〜I16、FR-I20〜I29、FR-I30〜I32、FR-I50〜I54、FR-E12
詳細仕様: [04-csv-format.md](04-csv-format.md)

1. `events` への `external_key` と `import_batch_id` の追加
   — **`external_key` は一意制約にしない。** 重複だと分かったうえで
   そのまま入れる選択（FR-I21）ができなくなるため。検索用の索引だけ張る
2. 標準CSV形式の解析とプレビュー（`/api/import/parse`）
3. 担当者・カレンダーの一括指定と、取り込みの実行（`/api/import/commit`）
4. `external_key` による重複検出
5. **取り込み履歴の画面と、バッチ単位の削除・復元**（設定 → 取り込みの中に置く）
6. 「仮」「中止」の表示（取り消し線、中止の表示切替）

**取り込みと一括削除は同じステップで作る。** 削除が無い状態で取り込みだけを
使い始めると、間違えた取り込みを1件ずつ消す羽目になる。

**完了の目安**: 受け入れ基準 AC-12〜AC-19 を満たす。
サッカー1シーズン分（数百件）を取り込み → 削除 → 取り込み直し まで通す。

この段階では手書きのCSVで確認すればよい。
football-data.org からのCSV生成は別プログラムの作業になる。

**.ics と文字コードの自動判定（FR-I01・FR-I04）は Step 7 に回した。**
まず使うのは自分で作る CSV（UTF-8）なので、先に一周させることを優先した。

### Step 7: 取り込みの繰り返しを楽にする（実装済み）

対応する要件: FR-I01〜I05、FR-I15、FR-I17〜I19

1. 列の指定画面と、文字コードの自動判定
2. **取り込みの設定を名前を付けて残す**（担当者・列の対応・重複時の動作・文字コード）
3. 取り込み画面の手順説明（年1回でも迷わないように）
4. `.ics` の取り込み

**文字コードはライブラリを入れずに判定する。**
UTF-8 として厳密に読んでみて、失敗したら Shift_JIS。
外したときのために、画面で選び直せるようにもしてある。

**.ics で読むのは VEVENT の中の必要な項目だけ。**
招待・出欠・添付・アラームは読まない（このアプリに置き場が無い）。
時間帯は TZID の名前（`Asia/Tokyo` など）で解釈し、
ファイルに書かれた VTIMEZONE の切り替え規則は読まない。
名前が IANA の形なら、規則は端末側が持っているもので足りる。
繰り返し（RRULE）はそのまま引き継ぐ（Step 5 の仕組みに乗る）。

**まだ作っていないもの**: .zip の書き出し（FR-I07・Could）、
URL の購読（FR-I08・Later）。

**完了の目安**: 受け入れ基準 AC-10〜AC-11、AC-20 を満たす。
毎月の休日ファイルを「設定を選ぶ → ファイルを渡す → プレビュー → 実行」の
3操作で取り込める。

### Step 8: デスクトップアプリ

対応する要件: 9.5 節、NFR-C01、NFR-O03

- Tauri のシェルを作り、デプロイ済みウェブアプリを表示する
- OS通知、トレイ常駐
- グローバルショートカットとクイック入力
- ファイルのドラッグ&ドロップから取り込み画面へ
- 自動更新とインストーラの配布

**完了の目安**: 受け入れ基準 AC-02、AC-23 を満たす。

### Step 9: 仕上げ

- 通知・リマインダー（FR-N01〜N04）
- 検索（FR-S01〜S02）
- 祝日表示（FR-V11）
- Realtime による自動反映（FR-V08）
- .ics エクスポート（FR-I40）

## この後

スケジュール管理が日常的に使える状態になってから、次の機能に着手する。
Step 1 で作った家族・メンバーと RLS の仕組みは、以降の機能でもそのまま使う。

先に複数の機能を並行して作り始めると、どれも中途半端で使えないまま終わる。
1機能ずつ「使える状態」にすることを優先する。

### 残りの機能と、作る順番の考え方

| 機能 | 規模の見込み | 前提になるもの |
| --- | --- | --- |
| 習慣管理 | 小さい | Step 5 の繰り返し展開、メンバー、Step 2.5 のシェル |
| 家計簿 | 大きい | メンバー、日付、Step 2.5 のシェル |
| 献立管理 | 中くらい | 家計簿（食費との連携）、日付、Step 2.5 のシェル |

画面の並べ方は [06-app-shell.md](06-app-shell.md) で決めてある。
どの機能から作っても、メニューへの載せ方は同じになる。

**習慣管理を先にするのを勧める。** 理由は2つ。

- Step 5 で作る繰り返しの展開をそのまま使えるので、
  新しく作るのは画面と記録の部分だけになる。3つの中で一番小さい
- 献立管理は買い物の結果を家計簿の食費として記録したいので、
  家計簿より先に作っても片手落ちになる。順番が後ろに固定される

そのため **スケジュール → 習慣 → 家計簿 → 献立** を素案とする。
ただし、家計簿のほうが日々の困りごととして大きいなら順番を入れ替えてよい。
決めるのは第1弾が動いてからで間に合う。
