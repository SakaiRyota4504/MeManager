## 1. 採用する技術

| 層 | 技術 | 備考 |
| --- | --- | --- |
| ウェブアプリ | Next.js (App Router) + TypeScript | 確定 |

## 3. デスクトップアプリに Tauri を選ぶ理由

Next.js と組み合わせる前提で候補を比較した。

| 候補 | 長所 | 短所 |
| --- | --- | --- |
| **Tauri v2**（推奨） | 配布サイズが数十MBと小さく、常駐しても軽い。通知・トレイ・グローバルショートカット・自動更新を標準で持つ。将来モバイルにも展開できる | Rust のビルド環境が必要 |
| Electron | 情報量が多い。Next.js との組み合わせ事例も豊富 | 配布サイズ100MB超、メモリ消費が大きい。常駐前提だと不利 |
| PWA のみ | 実装が1つで済む | グローバルショートカットや常駐ができず、「操作性重視」の要求を満たしにくい |

常駐して通知を出し、ショートカットで素早く入力する使い方を想定しているため Tauri を推す。

### 3.1 デスクトップ版の作り方（2段階）

**第1段階: 薄いシェル**

Tauri のウィンドウで、デプロイ済みのウェブアプリ（Vercel の URL）を読み込む。
デスクトップ固有の実装は、ネイティブ機能だけに限定する。

- OS通知
- タスクトレイ常駐と「今日の予定」表示
- グローバルショートカット（クイック入力ウィンドウの呼び出し）
- ローカルファイルの読み込み（インポート機能で使う）

この方式なら、ウェブ版を更新するだけでデスクトップ版の中身も更新される。
アプリの再配布が要るのはネイティブ部分を変えたときだけになる。

**第2段階: ローカル同梱（必要になったら）**

起動速度やオフライン参照が問題になった時点で、
Next.js を静的出力してアプリに同梱する方式へ切り替える。
第1段階の作りを大きく壊さずに移行できる。

最初から第2段階を目指すと、Next.js の静的出力の制約（Route Handler や middleware が使えない）に
早々にぶつかるため、段階を分ける。

## 4. Supabase の使い方

### 4.1 認証

Supabase Auth を使う。自前でパスワードをハッシュ化して保存する実装は書かない。

- 方式: メールアドレス + パスワード
- セッション: `@supabase/ssr` によるCookieベースのセッション管理
- 家族への追加: **管理者が登録する**（アプリにサインアップ画面は置かない）
- Google ログイン等の外部IdPは、Supabase の設定で後から追加できる。初期は実装しない

### 4.2 認可は RLS（Row Level Security）で行う

Supabase を使う最大の利点は、認可をデータベース側に寄せられること。
「他の家族のデータが見えてしまう」事故を、アプリ側の実装ミスから切り離せる。

方針:

- すべてのテーブルで RLS を有効にする
- 「要求者がその行の属する家族のメンバーであること」をポリシーで表現する
- アプリのコードで家族IDを `WHERE` に付け忘れても、データは漏れない状態にする

ポリシーの具体は [02-schedule-requirements.md](02-schedule-requirements.md) の
データモデル節に記述する。

### 4.3 データアクセスの使い分け

| 処理 | 方法 |
| --- | --- |
| 単純な取得・作成・更新・削除 | クライアントから supabase-js で直接アクセス（RLS が守る） |
| 繰り返し予定の展開 | Next.js の Route Handler |
| 一括インポートの解析・登録 | Next.js の Route Handler |
| 複数テーブルにまたがる整合性が必要な処理 | Postgres 関数（RPC）またはトランザクション |

サービスロールキー（RLS を迂回する鍵）はサーバ側だけで使い、
クライアントに配布するのは anon キーのみとする。

### 4.4 リアルタイム反映

Supabase Realtime で `events` テーブルの変更を購読する。
家族の誰かが予定を追加すると、他の端末の画面に自動で反映される。

ポーリングを自前で実装する必要はない。
接続が切れている間の変更に備え、ウィンドウがフォーカスされたタイミングで再取得も行う。

### 4.5 Storage

インポートするファイル（.ics / CSV）の一時保管に使う。
取り込み完了後は削除する。将来の家計簿機能ではレシート画像の保管に使う。

## 5. ディレクトリ構成（案）

画面は**機能ごとに区切る**。並べ方は [06-app-shell.md](06-app-shell.md)。

```
memanager/
├─ apps/
│  ├─ web/src/
│  │  ├─ app/
│  │  │  ├─ (auth)/         … ログイン
│  │  │  ├─ (app)/          … ログイン後。ここだけがメニューを持つ
│  │  │  │  ├─ layout.tsx   … メニューを並べる場所
│  │  │  │  ├─ schedule/    … スケジュール管理
│  │  │  │  ├─ habits/      … 習慣管理（これから）
│  │  │  │  ├─ budget/      … 家計簿（これから）
│  │  │  │  ├─ meals/       … 献立管理（これから）
│  │  │  │  └─ settings/    … 設定（メンバーなど）
│  │  │  └─ api/            … Route Handler（繰り返し展開・インポート処理）
│  │  ├─ components/        … 画面をまたいで使う部品（フォーム、メニュー）
│  │  ├─ lib/
│  │  │  ├─ nav/            … 機能の一覧。メニューはここから作る
│  │  │  ├─ supabase/       … クライアント生成、型定義
│  │  │  ├─ calendar/       … 日付の計算
│  │  │  ├─ recurrence/     … 繰り返し予定の展開（これから）
│  │  │  └─ import/         … ics / CSV の解析（これから）
│  │  └─ proxy.ts           … セッション更新（Next.js 16 で middleware から改名）
│  └─ desktop/              … Tauri（Rust）のシェルとネイティブ機能（これから）
├─ supabase/
│  ├─ migrations/           … DBスキーマのマイグレーション
│  ├─ schema.sql            … migrations をまとめた写し（SQL Editor 用）
│  └─ tests/                … RLS の検証
└─ docs/
```

機能ごとのフォルダは、その機能の画面だけを持つ。
画面をまたいで使うものだけを `components/` と `lib/` に置く。
