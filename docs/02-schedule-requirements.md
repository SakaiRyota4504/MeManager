# スケジュール管理 要件定義

対象: MeManager 第1弾機能「スケジュール管理」
前提技術: Next.js + Supabase / デスクトップは Tauri（[01-architecture.md](01-architecture.md)）
状態: ドラフト（未確定事項は「13. 要確認事項」を参照）

---

## 1. 位置づけとゴール

家族の予定を1つのカレンダーに集約し、
**「見たい人の予定だけを見られる」**状態をつくる。

全員の予定が混ざったままでは、自分に関係ない予定がノイズになって使われなくなる。
そのため本機能では、次の2点を中心的な要求として扱う。

1. **予定は必ず「誰の予定か」を持つ** — 担当者の入力を必須にする
2. **人単位で絞り込める** — 「自分の予定だけ」をすぐ表示できる

加えて、サッカーの試合日程のようにまとまった予定を手入力するのは現実的でないため、

3. **外部データの取込** — 手元のファイル（.ics / CSV）の一括登録と、
   football-data.org のような外部サービスのデータを継続的に反映する仕組み

を第1弾の必須機能とする。

このフェーズでは機能を広げるより土台を正しく作ることを優先する。
特に「家族・メンバー」「日付とタイムゾーン」「繰り返しのデータ構造」は、
後から直すと家計簿・献立にも影響する。

## 2. 用語

| 用語 | 意味 |
| --- | --- |
| 家族（Family） | データを共有する単位。ユーザはいずれか1つ以上の家族に属する |
| メンバー（Member） | 家族に属するユーザ。予定の担当者になれる |
| カレンダー（Calendar） | 予定をまとめる入れ物。色とアクセス範囲を持つ（例: 「家族共有」「サッカー」） |
| 予定（Event） | 1件の予定。繰り返し設定を持つ場合がある |
| 担当者（Assignee） | その予定が「誰の予定か」を示すメンバー。1件につき1人以上必須 |
| 発生（Occurrence） | 繰り返し予定を展開した結果の、特定日時における1回分 |
| 例外（Exception） | 繰り返しのうち特定の1回だけを変更・削除した記録 |
| 終日予定 | 時刻を持たず日付だけを持つ予定（例: 「旅行」「燃えるゴミ」） |
| 取り込みバッチ（Import Batch） | ファイル取込1回分の単位。まとめて取り消せる |
| フィード（Feed） | 外部データの取込口。継続的に同期される予定の集合（例: 「プレミアリーグ 2026-27」） |
| 外部キー（External Key） | 外部データ側での予定の識別子。同じ予定を二重登録しないために使う |

## 4. 機能要件

優先度は **Must**（第1弾に必須）／**Should**（第1弾に入れたい）／**Could**（余力があれば）／**Later**（フェーズ2以降）。

### 4.1 認証・家族管理

| ID | 要件 | 優先度 |
| --- | --- | --- |
| FR-A01 | メールアドレスとパスワードでサインアップ・ログイン・ログアウトができる（Supabase Auth） | Must |
| FR-A02 | 初回サインアップ時に家族が1つ作成され、作成者が管理者になる | Must |
| FR-A03 | 管理者は招待リンクを発行できる。リンクには有効期限（既定7日）がある | Must |
| FR-A04 | 招待リンクから参加したユーザは、その家族のメンバーになる | Must |
| FR-A05 | メンバーは表示名と自分の色を設定できる | Must |
| FR-A06 | **実在しない人物（例: 未登録の子ども）をメンバーとして登録できる** | Must |
| FR-A07 | 管理者はメンバーを家族から外せる | Should |
| FR-A08 | パスワードを再設定できる | Should |
| FR-A09 | ログイン状態は明示的にログアウトするまで保持される | Must |

FR-A06 の補足: 担当者を必須にする以上、
アカウントを持たない家族（幼い子どもなど）も担当者として選べる必要がある。
そのため「メンバー」を「ログインユーザ」と切り離し、
アカウント未紐付けのメンバー（プロフィールのみ）を作れるようにする。
後からアカウントを作ったときに紐付けられる。

| 場所 | | 0〜200文字 |
| メモ | | 0〜2000文字 |
| 色 | | 未指定なら担当者またはカレンダーの色を継承 |
| 状態 | ○ | `確定` / `仮` / `中止`。既定は `確定` |
| 繰り返し | | 4.5 を参照 |
| 通知 | | 4.8 を参照 |

### 4.4 担当者とフィルタ

本機能の中心。

| ID | 要件 | 優先度 |
| --- | --- | --- |
| FR-M01 | 予定には担当者を1人以上指定する。0人では保存できず、その旨をフォーム上で示す | Must |
| FR-M02 | 担当者は複数指定できる（例: 「家族旅行」は全員、「授業参観」は母と子） | Must |
| FR-M03 | 「全員」を1操作で選択できるボタンを用意する | Must |
| FR-M04 | 予定作成時、担当者の初期値は作成者自身とする | Must |
| FR-M05 | メンバー単位で表示／非表示を切り替えられる | Must |
| FR-M06 | **「自分の予定だけ」をワンクリック（およびショートカット）で表示できる** | Must |
| FR-M07 | 絞り込みの状態はユーザ設定として保存され、次回起動時・別端末でも引き継がれる | Should |
| FR-M08 | 絞り込みの状態は URL に反映され、再読み込みしても保たれる | Should |
| FR-M09 | 絞り込み中はその旨が画面上で明示され、解除操作がすぐ見つかる | Must |
| FR-M10 | カレンダー単位でも表示／非表示を切り替えられる（メンバーの絞り込みと併用） | Must |
| FR-M11 | 予定はカード上に担当者が分かる形（色・アイコン）で表示される | Must |

**「全員」の扱いについての設計判断**

「全員」は特別な値ではなく、**その時点の全メンバーを担当者として展開して保存する**。

| 方式 | 長所 | 短所 |
| --- | --- | --- |
| **全メンバーを展開して保存**（採用） | 絞り込みが「担当者に含まれるか」の単純な判定で済む。表示も一貫する | 後からメンバーが増えても、過去の予定に自動追加されない |
| 「全員」フラグを持たせる | メンバー増減に自動追従する | 絞り込み・表示の条件分岐が全箇所に増える |

家族の増減は頻繁ではなく、必要なら予定を編集すればよい。
判定ロジックを単純に保つ利点のほうが大きいと判断した。

### 4.7 外部データの取込

取込の経路は2つある。用途が違うので、仕様も分ける。

| 経路 | 用途 | 形式 | 実行者 | 再実行したとき |
| --- | --- | --- | --- | --- |
| **A. ファイル取込** | 手元にあるファイルを1回だけ入れる | .ics / CSV | 人 | 重複を検出してスキップ |
| **B. フィード同期** | 外部サービスのデータを継続的に反映する | JSON（本アプリが定める形式） | 変換プログラム | 外部キーで照合して更新 |

football-data.org の試合日程は **経路B** で扱う。
試合はキックオフ時刻の確定や延期・中止で内容が変わるため、
「1回入れて終わり」ではなく、何度でも送り直せる仕組みが要る。

経路Bの詳細な仕様（JSON の形式、football-data.org からの変換）は
[04-external-feeds.md](04-external-feeds.md) に分けて記述する。

#### 4.7.1 ファイル取込の対応フォーマット

| ID | 要件 | 優先度 |
| --- | --- | --- |
| FR-I01 | iCalendar 形式（.ics）を取り込める。Google カレンダー・Outlook の書き出しファイルを対象とする | Must |
| FR-I02 | CSV を取り込める。列の意味は取り込み時に指定する（列マッピング） | Must |
| FR-I03 | Google カレンダーの CSV 書き出し形式を、列マッピングなしで自動認識する | Should |
| FR-I04 | 文字コードは UTF-8 / UTF-8(BOM) / Shift_JIS を自動判定する | Must |
| FR-I05 | .ics に含まれる繰り返しルール（RRULE）を、繰り返し予定として取り込む | Should |
| FR-I06 | .ics のタイムゾーン定義（VTIMEZONE）を解釈する | Should |
| FR-I07 | .zip で書き出された Google カレンダーのファイルをそのまま受け付ける | Could |
| FR-I08 | 公開カレンダーの URL（.ics）を購読し、定期的に取り込む | Later |

FR-I04 の補足: 日本で配布される日程表の CSV は Excel 経由の Shift_JIS が多い。
自動判定に失敗した場合は、ユーザが手動で文字コードを選び直せるようにする。

#### ファイル取込の流れ

```
① ファイル選択     ドラッグ&ドロップ / ファイル選択ダイアログ
        ↓
② 解析            文字コード判定 → 形式判定 → 行・イベントの抽出
        ↓
③ 列マッピング     CSV のとき。どの列がタイトル・日付・場所かを指定
        ↓
④ 一括設定        取り込み先カレンダー、担当者（必須）、既定の通知
        ↓
⑤ プレビュー      取り込む内容の一覧、件数、期間、重複候補、警告行
        ↓
⑥ 実行            取り込みバッチとして登録
        ↓
⑦ 結果            登録N件 / スキップN件 / 失敗N件 と、取り消しへの導線
```

| ID | 要件 | 優先度 |
| --- | --- | --- |
| FR-I10 | 取り込み前に内容をプレビューでき、実行前に中止できる | Must |
| FR-I11 | **取り込む予定すべてに適用する担当者を指定できる（担当者必須のため省略不可）** | Must |
| FR-I12 | 取り込み先のカレンダーを指定できる。新規カレンダーをその場で作成できる | Must |
| FR-I13 | プレビュー上で、個々の行を取り込み対象から外せる | Should |
| FR-I14 | プレビュー上で、個々の行のタイトル・日時を修正できる | Could |
| FR-I15 | CSV の列マッピング設定に名前を付けて保存し、次回以降再利用できる | Could |
| FR-I16 | 日時として解釈できない行は「警告」として示し、取り込み対象から自動で外す | Must |

#### ファイル取込の重複と取り消し

| ID | 要件 | 優先度 |
| --- | --- | --- |
| FR-I20 | 既存の予定と重複する可能性のある行を検出し、プレビューで示す | Must |
| FR-I21 | 重複時の動作を選べる：スキップ／上書き／そのまま登録 | Must |
| FR-I22 | 重複判定は、.ics は UID、CSV は（タイトル・開始日時・カレンダー）の一致で行う | Must |
| FR-I23 | **取り込みは「バッチ」として記録され、その回の登録分だけをまとめて取り消せる** | Must |
| FR-I24 | 取り込み後に手で編集された予定は取り消し対象から除外し、その件数を伝える | Should |
| FR-I25 | 過去の取り込み履歴（日時・件数・実行者・取り込み元ファイル名）を一覧できる | Should |

FR-I23 の補足: 日程表の差し替えや取り込みミスは必ず起きる。
1件ずつ消す作業が発生すると、一括登録の利点が失われる。

#### ファイル取込の制限

| ID | 要件 |
| --- | --- |
| FR-I30 | 1ファイルあたり最大 2,000件 / 10MB までを受け付ける |
| FR-I31 | 上限を超えるファイルは、その旨を明示して受け付けない |
| FR-I32 | デスクトップアプリでもウェブでも同じ手順で取り込める |

#### 4.7.2 フィード同期

外部で生成したデータを、繰り返し送り込んで反映させる仕組み。
football-data.org のように「後から内容が変わる」データ源を対象とする。

##### フィードの登録

| ID | 要件 | 優先度 |
| --- | --- | --- |
| FR-F01 | 取込先として「フィード」を登録できる。フィードは名称・取込先カレンダー・既定の担当者を持つ | Must |
| FR-F02 | フィードごとに専用の取込トークンを発行できる。変換プログラムはこのトークンで取込APIを呼ぶ | Must |
| FR-F03 | 取込トークンは再発行・失効ができる | Should |
| FR-F04 | フィードを削除するとき、由来する予定を残すか消すかを選べる | Should |
| FR-F05 | フィード由来の予定は、画面上で出所（どのフィードから来たか）が分かる | Should |

FR-F02 の補足: 変換プログラムに Supabase のサービスロールキーを渡してはならない。
そのキーは家計簿を含む全データを操作できるため、
用途を「このフィードへの書き込みだけ」に限定したトークンを別に発行する。

##### 同期の動作

| ID | 要件 | 優先度 |
| --- | --- | --- |
| FR-F10 | 取込APIは本アプリが定める JSON 形式を受け付ける | Must |
| FR-F11 | 各予定は外部キー（`externalKey`）を持つ。同じキーの再送は新規作成ではなく更新になる | Must |
| FR-F12 | 同期リクエストは対象期間（`window`）を明示する | Must |
| FR-F13 | 期間内に存在するのにリクエストに含まれない予定は「消えた予定」として扱い、中止にする | Must |
| FR-F14 | 同じ内容を2回送っても、予定は重複せず件数だけが返る（冪等） | Must |
| FR-F15 | 1回のリクエストは最大1,000件までとする | Must |
| FR-F16 | 同期は担当者を伴う。フィードの既定担当者を使い、リクエストで個別に上書きもできる | Must |

FR-F12・FR-F13 の補足: 「送られてこなかったものを消す」判断には範囲の明示が要る。
2026年9月分だけを送ったときに、10月以降の予定まで消えては困る。
そのため、削除の判断を行う範囲をリクエスト側に必ず宣言させる。

##### 予定の状態

| ID | 要件 | 優先度 |

| カラム | 型 | 説明 |
| --- | --- | --- |
| event_id | uuid | |
| member_id | uuid | |

主キーは (event_id, member_id)。インデックスを `(member_id, event_id)` にも張る。

**1人以上を保証する方法**: 子テーブルなので `NOT NULL` では表現できない。

アプリ側のバリデーションだけに頼ると、インポート経路など別の入口から破られる。

## 7. RLS ポリシー

すべてのテーブルで RLS を有効にする。基本方針は
**「その行の `family_id` が、要求者の所属する家族のいずれかであること」**。

判定用のヘルパー関数を用意し、各ポリシーから呼ぶ。

```sql
-- 要求者が所属する家族のID一覧
create function public.my_family_ids()
returns setof uuid
language sql stable security definer
as $$
  select family_id from public.members
  where user_id = auth.uid() and is_active
$$;
```

| テーブル | SELECT | INSERT / UPDATE / DELETE |
| --- | --- | --- |
| families | `id in (select my_family_ids())` | 管理者ロールのみ |
| members | `family_id in (select my_family_ids())` | 管理者ロール、または自分自身の行 |
| calendars | 同家族、かつ `visibility = 'family'` または自分が所有者 | 同家族のメンバー |
| events | 同家族、かつ所属カレンダーが閲覧可能 | 同家族のメンバー |
| event_assignees | 親の events が閲覧可能 | 親の events が編集可能 |
| import_batches | 同家族 | 同家族のメンバー |
| event_feeds | 同家族。`token_hash` は返さない | 管理者ロール |
| feed_sync_runs | 同家族 | サーバのみ（取込APIが書く） |
| user_preferences | 自分の行のみ | 自分の行のみ |

注意点:

- ポリシー内で `members` を参照するため、再帰を避けるヘルパー関数は `security definer` にする
- `events` に `family_id` を冗長に持たせているのは、
  ポリシーで `calendars` への結合を毎回発生させないため（性能と可読性の両方に効く）
- フィード同期の取込APIは、ログインユーザではなく取込トークンで認証する。
  RLS の対象外になるため、**Route Handler 側でフィードの `family_id` に閉じた操作だけを行う**。
  トークンから解決した `feed_id` 以外の行に触れないことを、実装とテストで担保する

## 8. API

### 9.3 予定作成の操作

「10秒以内に追加できる」を満たすための要件。

- タイトル・担当者・日時だけで保存できる（他はすべて任意）
- 開いた直後、フォーカスはタイトル欄にある
- 担当者の初期値は作成者自身（FR-M04）。そのままでよければ操作不要
- 担当者は色付きアイコンの並びから選ぶ（プルダウンを開かせない）
- カレンダー上のクリックで作成した場合、その日時が初期値として入る
- `Ctrl/Cmd + Enter` で保存できる

### 9.4 一括インポート画面

CSV の列マッピングは、左に取り込んだ列、右に予定の項目を並べて対応づける。
プレビューは表形式で、行ごとに状態（取り込む／警告／重複）を色で示す。

担当者の指定欄は画面上部に固定し、未指定のまま実行できないようにする。

## 10. 繰り返し予定の扱い

### 10.1 保存方法

発生を1件ずつ行として保存する方法は取らない。
「毎週月曜、終了日なし」が無限行になるためである。
**1件の予定 + RRULE** で保存し、必要な期間だけ展開する。

ただし**一括インポートで取り込んだ予定は、原則として個別の予定として保存する**。
試合日程のように日付が不規則なものは繰り返しルールで表現できないため。

### 10.2 展開の場所

サーバ側（Route Handler）で展開する。理由は次の2点。

- デスクトップとウェブで展開ロジックが二重化するのを避ける
- 展開の不具合を1か所の修正で直せる

展開には RFC 5545 準拠のライブラリ（`rrule`）を用い、自前実装しない。

### 10.3 タイムゾーンと夏時間

予定は入力時のタイムゾーン（既定 `Asia/Tokyo`）を保持し、そのタイムゾーンで展開する。
日本には夏時間がないため当面は問題にならないが、
UTC 固定で展開すると将来の海外利用時にずれるため、最初からタイムゾーンを持たせる。

### 10.4 例外の考え方

「今週だけ休み」「来週だけ時間変更」は、元の予定を変えずに例外行として記録する。
元の繰り返しルールを保ったまま、個別の回を上書きできる。

| scope | 動作 |
| --- | --- |
| `this` | 対象回の `event_exceptions` を作る（`modified` または `cancelled`） |
| `thisAndFuture` | 元の RRULE に `UNTIL` を設定して打ち切り、対象回以降を新しい予定として作る |
| `all` | 元の予定そのものを更新／削除する |

## 11. 受け入れ基準

第1弾の完了条件。

| ID | 基準 |
| --- | --- |
| AC-01 | 2人以上のユーザが同じ家族に参加し、互いの予定を見られる |
| AC-02 | ウェブとデスクトップの両方から予定を作成でき、もう一方に反映される |
| AC-03 | 月・週・リストの3表示が動作し、期間の移動ができる |
| AC-04 | 終日予定と時刻付き予定が、それぞれ正しい位置に表示される |
| AC-05 | **担当者を選ばずに予定を保存しようとすると、保存できずその理由が示される** |
| AC-06 | **「自分の予定のみ」を選ぶと、自分が担当者の予定だけが残る** |
| AC-07 | **絞り込み中はその状態が画面上で分かり、1操作で解除できる** |
| AC-08 | 絞り込みの状態がリロード後・別端末でも引き継がれる |
| AC-09 | 毎週の繰り返し予定を登録でき、「この回のみ削除」が他の回に影響しない |
| AC-10 | Google カレンダーから書き出した .ics を取り込み、担当者を指定して登録できる |
| AC-11 | Shift_JIS の CSV を、列を対応づけて取り込める |
| AC-12 | 取り込み後に「この取り込みを取り消す」を実行すると、その分だけが消える |
| AC-13 | 同じファイルを2回取り込むと、2回目は重複として検出される |
| AC-14 | **フィードを登録して取込トークンを発行し、そのトークンで同期APIを呼べる** |
| AC-15 | **football-data.org 由来のデータを同期すると、試合が予定として表示される** |
| AC-16 | **同じデータを2回送っても予定が重複しない（件数が変わらない）** |
| AC-17 | **キックオフ時刻を変えたデータを送ると、既存の予定の時刻が更新される** |
| AC-18 | **中止になった試合が「中止」として残り、カレンダー上で中止と分かる** |
| AC-19 | **日程未確定の試合が「仮」として登録され、確定後の同期で時刻が入る** |
| AC-20 | **人がメモを追記した予定は、次の同期で上書きされない** |
| AC-21 | **対象期間の外にある予定が、同期によって消えない** |
| AC-22 | 画面幅375pxで、横スクロールなしに操作できる |
| AC-23 | 他の家族の予定IDを直接指定しても、内容が取得できない（RLS で遮断される） |
| AC-24 | あるフィードの取込トークンで、別のフィードや別の家族のデータを操作できない |
| AC-25 | デスクトップアプリで、キーボードのみで予定の作成から保存まで完了できる |

## 12. 第1弾のスコープ外

- Google カレンダーとの双方向同期（取り込みは行うが、継続同期はしない）
- .ics URL の定期購読
- 本アプリ内部から football-data.org を直接呼ぶこと（変換は別プログラムが行う）
- 試合結果（スコア）の自動反映
- 家族以外の人との予定調整・招待
- オフラインでの編集と競合解決
- Web Push（ブラウザを閉じている間の通知）
- 予定へのファイル添付
- 多言語対応
