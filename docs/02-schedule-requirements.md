# スケジュール管理 要件定義

対象: MeManager 第1弾機能「スケジュール管理」
前提技術: Next.js + Supabase / デスクトップは Tauri（[01-architecture.md](01-architecture.md)）
状態: ドラフト（未確定事項は「13. 要確認事項」を参照）

---

## 1. 位置づけとゴール

家族の予定を1つのカレンダーに集約し、
**「見たい人の予定だけを見られる」**状態をつくる。

全員の予定が混ざったままでは、自分に関係ない予定がノイズになって使われなくなる。
そのため本機能では、次の2点を中心的な要求として扱う。

1. **予定は必ず「誰の予定か」を持つ** — 担当者の入力を必須にする
2. **人単位で絞り込める** — 「自分の予定だけ」をすぐ表示できる

加えて、サッカーの試合日程のようにまとまった予定を手入力するのは現実的でないため、

3. **外部データの取込** — 手元のファイル（.ics / CSV）の一括登録と、
   football-data.org のような外部サービスのデータを継続的に反映する仕組み

を第1弾の必須機能とする。

このフェーズでは機能を広げるより土台を正しく作ることを優先する。
特に「家族・メンバー」「日付とタイムゾーン」「繰り返しのデータ構造」は、
後から直すと家計簿・献立にも影響する。

## 2. 用語

| 用語 | 意味 |
| --- | --- |
| 家族（Family） | データを共有する単位。ユーザはいずれか1つ以上の家族に属する |
| メンバー（Member） | 家族に属するユーザ。予定の担当者になれる |
| カレンダー（Calendar） | 予定をまとめる入れ物。色とアクセス範囲を持つ（例: 「家族共有」「サッカー」） |
| 予定（Event） | 1件の予定。繰り返し設定を持つ場合がある |
| 担当者（Assignee） | その予定が「誰の予定か」を示すメンバー。1件につき1人以上必須 |
| 発生（Occurrence） | 繰り返し予定を展開した結果の、特定日時における1回分 |
| 例外（Exception） | 繰り返しのうち特定の1回だけを変更・削除した記録 |
| 終日予定 | 時刻を持たず日付だけを持つ予定（例: 「旅行」「燃えるゴミ」） |
| 取り込みバッチ（Import Batch） | ファイル取込1回分の単位。まとめて取り消せる |
| 外部キー（External Key） | 外部データ側での予定の識別子。取り込み直したときに、二重登録せず更新するために使う |

## 4. 機能要件

優先度は **Must**（第1弾に必須）／**Should**（第1弾に入れたい）／**Could**（余力があれば）／**Later**（フェーズ2以降）。

| --- | --- | --- |
| FR-A01 | メールアドレスとパスワードでログイン・ログアウトができる（Supabase Auth） | Must |
| FR-A02 | **アカウントを持てるのは、管理者がメンバーとして登録した人だけとする** | Must |
| FR-A03 | **アプリにサインアップ画面を置かない。最初の1人は Supabase 側でユーザーを作る** | Must |
| FR-A04 | 最初に登録した人が家族の管理者になり、家族と既定カレンダーが作られる | Must |
| FR-A05 | **管理者はメンバーを登録できる。表示名だけの登録と、ログイン付きの登録を選べる** | Must |
| FR-A06 | **ログイン付きで登録するとき、管理者がメールアドレスとパスワードを決めて本人に伝える** | Must |
| FR-A06b | **アカウントを Supabase 側で作る場合に備え、メンバーにログイン用のメールアドレスだけを登録できる** | Must |
| FR-A07 | **表示名だけで登録した人に、あとからログインを設定できる** | Must |
| FR-A08 | **1人のメンバーに紐付くアカウントは1つまで** | Must |
| FR-A09 | **管理者はメンバーを家族から外せる。外した時点でデータが見えなくなる** | Must |
| FR-A10 | 外したメンバーは戻せる。行は削除しないので過去の予定の担当者は保たれる | Must |
| FR-A11 | **実在しない人物（例: 未登録の子ども）をメンバーとして登録できる** | Must |
| FR-A12 | メンバーは表示名と自分の色を設定できる。管理者は他のメンバーの表示名と家族の名前も変えられる | Must |
| FR-A13 | 管理者はメンバーの役割を変更できる。管理者が0人になる変更は拒否する | Should |
| FR-A14 | 本人がパスワードを変更できる | Should |
| FR-A15 | ログイン状態は明示的にログアウトするまで保持される | Must |

**招待の仕組みは作らない**

一度は招待リンク方式で実装したが、家族だけで使うアプリには重かったため取りやめた。

| | 招待リンク方式（不採用） | 管理者が登録する方式（採用） |
| --- | --- | --- |
| 手順 | 管理者がリンクを発行 → 相手が開いて自分で登録 | 管理者が登録して、メールとパスワードを伝える |
| 覚えること | リンクの受け渡し、有効期限、取り消し | 追加するだけ |
| リンクが漏れたら | こちらが用意していない枠にアカウントが増える | **枠が無いので増えようがない** |
| 画面 | 招待の発行・一覧・取り消し・受諾の4つ | メンバーの追加1つ |

**アカウントが生まれる経路は「管理者が用意したメンバーに紐付ける」1本だけ**になる。
名前だけのメンバー（小さい子ども）と、ログインする人の登録手順も同じ流れに揃う。

**アカウントの作成を閉じる方法**

次の3層で塞ぐ。1つが破られても、残りが効く。

| 層 | 内容 |
| --- | --- |
| 1. アプリ | **サインアップ画面を置かない。**ログイン画面にアカウント作成への導線は無い |
| 2. Supabase Auth | 公開サインアップを無効にする（`enable_signup = false`）。`/auth/v1/signup` は誰が叩いても拒否される |
| 3. データベース | サインアップのトリガーが、紐付け先のメンバーを探せなければユーザーの作成ごと失敗させる |

3層目が最後の砦になる。1と2を迂回してユーザーが作られても、
紐付け先のメンバーが無ければトランザクションごと失敗し、アカウントは残らない。

**アカウントが生まれる経路**は次の3つだけで、どれも管理者の操作から始まる。

| 経路 | 紐付け先の決め方 |
| --- | --- |
| 最初の1人 | まだ家族が1つも無いときに限り、家族とメンバーを新しく作る |
| メンバー画面から | 管理者が用意したメンバーを `member_id` で指定する |
| Supabase の管理画面から | 管理者が先に登録した `members.login_email` と、ユーザーのメールアドレスが一致するメンバー |

3つ目があるので、Supabase のダッシュボードからユーザーを作る運用もできる。
そのときも「枠を先に作るのは管理者だけ」という性質は変わらない。

**メンバー行の更新は列ごとに絞る。** `members` の更新ポリシーは
「管理者、または自分の行」を許すが、ポリシーでは列を絞れないため、
本人が `role` を `admin` に書き換えたり、`family_id` を別の家族に
付け替えて他人のデータを読んだりできてしまう。
トリガー（`guard_member_update`）で、本人が変えられるのを表示名と色だけに限る。

FR-A08 の補足: トリガーは `user_id is null` のメンバーにしか紐付けない。
すでにアカウントがある人に2つ目を付けることはできない。

FR-A09 の補足: メンバーを外すときは行を削除せず `is_active` を false にする。
過去の予定の担当者として名前が残る必要があるため。
RLS の判定に使う `my_family_ids()` が `is_active` で絞っているので、
false にした時点でその人からはデータが一切見えなくなる。
外した人が入り直す経路は無い（管理者が戻すまで何もできない）。

FR-A11 の補足: 担当者を必須にする以上、
アカウントを持たない家族（幼い子どもなど）も担当者として選べる必要がある。
そのため「メンバー」を「ログインユーザ」と切り離し、
アカウント未紐付けのメンバー（プロフィールのみ）を作れるようにする。
後からアカウントを作ったときに紐付けられる。

**「全員」の扱いについての設計判断**

「全員」は特別な値ではなく、**その時点の全メンバーを担当者として展開して保存する**。

| 方式 | 長所 | 短所 |
| --- | --- | --- |
| **全メンバーを展開して保存**（採用） | 絞り込みが「担当者に含まれるか」の単純な判定で済む。表示も一貫する | 後からメンバーが増えても、過去の予定に自動追加されない |
| 「全員」フラグを持たせる | メンバー増減に自動追従する | 絞り込み・表示の条件分岐が全箇所に増える |

家族の増減は頻繁ではなく、必要なら予定を編集すればよい。
判定ロジックを単純に保つ利点のほうが大きいと判断した。

### 4.7 外部データの取込

取込の入口は **ファイルの取り込み1つ** に統一する。
アプリが外部サービスを直接呼ぶことはしない。

取り込むファイルの出どころは2種類あるが、画面も処理も同じものを使う。

| ファイルの出どころ | 例 | 形式 |
| --- | --- | --- |
| 人が受け取ったファイル | 子どものチームから配られた日程表、Google カレンダーの書き出し | .ics / 任意の CSV（列マッピングで対応） |
| プログラムが生成したファイル | football-data.org から取得して変換したもの | **MeManager 標準CSV形式**（列マッピング不要） |

football-data.org の試合日程は後者にあたる。
取得と変換は本アプリの外で行い、標準CSV形式のファイルにして取り込む。
どのデータ源が増えても、本アプリ側は無改修で対応できる。

標準CSV形式の定義と、football-data.org からの作り方は
[04-csv-format.md](04-csv-format.md) に記述する。

#### 利用頻度の前提

取り込みは想定される使い方が2つあり、頻度が大きく違う。
機能の重みづけはこの前提に従う。

| 用途 | 頻度 | 1回の件数 | 性格 |
| --- | --- | --- | --- |
| 休日の取り込み | **月1回** | 数件〜十数件 | 毎月同じ形式のファイルが来る定型作業 |
| サッカーの年間日程 | **年1回** | 数百件 | 年に一度の大仕事 |

#### 操作モデル: 塊で入れて、塊で消す

取り込みの操作は、この1つの考え方で貫く。

```
   取り込み  ──────▶  1つの「バッチ」として記録される
                              │
                    間違えた／日程が変わった
                              │
                              ▼
   バッチごと削除  ──────▶  その回に入った予定だけが消える
                              │
                              ▼
   新しいファイルで取り込み直す
```

**個々の予定を1件ずつ直す操作を、取り込みの後始末として要求しない。**
入れ直したいときは、まとめて消してから入れ直す。
これなら覚えることが「取り込む」と「その回を消す」の2つで済む。

ここから導かれること。

- **月1回の取り込みは日常操作**である。毎月同じ列・同じ担当者・同じカレンダーを
  指定し直すのは手間なので、**取り込み設定を名前を付けて保存**できるようにする（FR-I17）。
  2回目以降は「プリセットを選んでファイルを渡すだけ」で済ませる。
- **年1回の取り込みは手順を忘れる。** 画面に説明を置き、
  プレビューで何が起きるかを丁寧に示す。
- **自動化は要らない。** 年13回程度の操作のために、
  外部から自動で書き込む仕組みを作る必要はない（12章）。
- **取り込み直しによる自動更新は作らない。**
  「消して入れ直す」で足りるものを、差分更新の仕組みで置き換えると、

#### 4.7.2 取り込みの流れ

```
① ファイル選択     ドラッグ&ドロップ / ファイル選択ダイアログ
        ↓
② 解析            文字コード判定 → 形式判定 → 行・イベントの抽出
        ↓
③ 列マッピング     標準CSV形式・.ics のときは飛ばす
                  それ以外の CSV で、どの列がタイトル・日付・場所かを指定
        ↓
④ 一括設定        取り込み先カレンダー、担当者、既定の通知
                  CSV の列で指定されていればそちらが優先される
        ↓
⑤ プレビュー      登録N件 / 重複でスキップN件 / 警告N件 の内訳と、対象期間
        ↓
⑥ 実行            取り込みバッチとして登録
        ↓
⑦ 結果            登録N件 / スキップN件 と、このバッチを削除するための導線
```

**終日と時刻付きで列を分ける理由**: 終日予定をタイムゾーン付きの日時で持つと、
タイムゾーンをまたいだ瞬間に日付がずれる（旅行先で「今日のゴミ出し」が前日に見える）。
終日は `date` 型で持ち、変換対象から外すことでこの問題を構造的に防ぐ。

インデックス:

- `(family_id, starts_at) WHERE deleted_at IS NULL`
- `(family_id, start_date) WHERE deleted_at IS NULL`
- `(import_batch_id)` — バッチの一括削除で使う
- `(family_id, external_key) WHERE external_key IS NOT NULL AND deleted_at IS NULL`
  — 部分一意インデックス。重複検出に使う

2つ目の `deleted_at IS NULL` が重要。
これを付け忘れると、バッチを削除してから同じファイルを取り込み直したときに
一意制約に引っかかり、**入れ直せなくなる**。
「消して入れ直す」が主な操作である以上、ここは必ず部分インデックスにする。
- タイトル・メモ・場所に対する全文検索インデックス（`pg_trgm`）

### event_assignees

| カラム | 型 | 説明 |
| --- | --- | --- |
| event_id | uuid | |
| member_id | uuid | |

主キーは (event_id, member_id)。インデックスを `(member_id, event_id)` にも張る。

**1人以上を保証する方法**: 子テーブルなので `NOT NULL` では表現できない。
予定の作成・更新は Postgres 関数（RPC）経由に統一し、その中で担当者の件数を検証する。

アプリ側のバリデーションだけに頼ると、インポート経路など別の入口から破られる。

## 7. RLS ポリシー

すべてのテーブルで RLS を有効にする。基本方針は
**「その行の `family_id` が、要求者の所属する家族のいずれかであること」**。

判定用のヘルパー関数を用意し、各ポリシーから呼ぶ。

```sql
-- 要求者が所属する家族のID一覧
create function public.my_family_ids()
returns setof uuid
language sql stable security definer
as $$
  select family_id from public.members
  where user_id = auth.uid() and is_active
$$;
```

| テーブル | SELECT | INSERT / UPDATE / DELETE |
| --- | --- | --- |
| families | `id in (select my_family_ids())` | 管理者ロールのみ |
| members | `family_id in (select my_family_ids())` | 管理者ロール、または自分自身の行 |
| calendars | 同家族、かつ `visibility = 'family'` または自分が所有者 | 同家族のメンバー |
| events | 同家族、かつ所属カレンダーが閲覧可能 | 同家族のメンバー |
| event_assignees | 親の events が閲覧可能 | 親の events が編集可能 |
| import_batches | 同家族 | 同家族のメンバー |
| user_preferences | 自分の行のみ | 自分の行のみ |

注意点:

- ポリシー内で `members` を参照するため、再帰を避けるヘルパー関数は `security definer` にする
- `events` に `family_id` を冗長に持たせているのは、
  ポリシーで `calendars` への結合を毎回発生させないため（性能と可読性の両方に効く）

## 8. API

Supabase を使うため、単純な取得・更新は supabase-js から直接行い、
ロジックが要るものだけ Next.js の Route Handler または Postgres 関数（RPC）に置く。

### 8.1 クライアントから直接（RLS が保護）

| 操作 | 方法 |
| --- | --- |
| カレンダー一覧の取得 | `from('calendars').select()` |
| メンバー一覧の取得 | `from('members').select()` |
| 予定の詳細取得 | `from('events').select('*, event_assignees(*)')` |
| 表示設定の保存 | `from('user_preferences').upsert()` |
| 予定の変更購読 | `channel().on('postgres_changes', ...)` |

### 8.2 Postgres 関数（RPC）

| 関数 | 説明 |
| --- | --- |
| `create_event(payload jsonb)` | 予定と担当者を1トランザクションで作成。担当者0人を拒否する |
| `update_event(event_id, scope, occurrence_start, patch jsonb)` | 繰り返しの編集範囲を考慮した更新 |
| `delete_event(event_id, scope, occurrence_start)` | 同上 |
| `undo_import_batch(batch_id)` | 取り込みバッチに属する予定をまとめて論理削除する |
| `redo_import_batch(batch_id)` | 30日以内なら取り消しを元に戻す |

### 8.3 Route Handler（Next.js）

| メソッド | パス | 説明 |
| --- | --- | --- |
| GET | `/api/events` | 期間内の予定を、繰り返しを展開して返す |
| GET | `/api/events/search` | キーワード検索 |
| POST | `/api/import/parse` | ファイルを解析し、プレビュー用のデータを返す（DBには書かない） |
| POST | `/api/import/commit` | プレビューの内容を確定し、取り込みバッチとして登録する |
| GET | `/api/export/ics` | .ics 形式で書き出す |

### 9.3 予定作成の操作

「10秒以内に追加できる」を満たすための要件。

- タイトル・担当者・日時だけで保存できる（他はすべて任意）
- 開いた直後、フォーカスはタイトル欄にある
- 担当者の初期値は作成者自身（FR-M04）。そのままでよければ操作不要
- 担当者は色付きアイコンの並びから選ぶ（プルダウンを開かせない）
- **追加の入口はカレンダーのマス。**大きなボタンは置かない（9.5 節）
- **開始と終了は常に同じ位置に出す。**終日にしても日付の欄は消さず、
  時刻の欄だけを止める。切り替えるたびに欄が入れ替わると、
  どこを触っていたか分からなくなる
- **カレンダー（予定の入れ物）は選ばせない。**「家族共有」1つだけを使う。
  複数のカレンダーを作れるようにするのは、必要が出てから
- カレンダー上のクリックで作成した場合、その日付が初期値として入る。
  開始日を動かすと、終了日も同じだけ動く（終了が開始より前になるのを防ぐ）
- `Ctrl/Cmd + Enter` で保存できる

### 9.4 一括インポート画面

CSV の列マッピングは、左に取り込んだ列、右に予定の項目を並べて対応づける。
プレビューは表形式で、行ごとに状態（取り込む／警告／重複）を色で示す。

担当者の指定欄は画面上部に固定し、未指定のまま実行できないようにする。

### 9.5 画面幅ごとの作り分け

**カレンダーは左右に余白を置かず、画面の端まで使う。**
1マスの幅はほぼ「画面幅 ÷ 7」になる。余白を置くとそのぶんマスが狭まり、
予定名が読めなくなるため、本文の読みやすさより横幅を優先する。
カレンダー以外の画面（メンバーなど）は、これまでどおり中央に寄せる。

**縦も、残っている高さを全部使う。** マスの高さは決め打ちにせず、
行が `1fr` で分け合う。画面が広ければマスが伸び、
狭ければ下限（幅によって 108 / 82 / 94px）で止まって縦にスクロールする。

**「予定を追加」のボタンは置かない。** マスを押せばその日で追加でき、
ボタン1つのために1行（約50px）をカレンダーから削るのは割に合わない。
一覧表示のときの入口として、月の移動と同じ行に小さな＋だけを置く。

**既定の表示は画面幅によらず月表示。** 一覧は切り替えで出す。
狭い画面でも「今月どうなっているか」を最初に見たいという判断。

| 画面幅 | 月表示のチップ |
| --- | --- |
| 861px 以上 | 11px・1行・**時刻あり** |
| 521〜860px | 10px・1行・時刻なし |
| 520px 以下 | 9.5px・**2行折り返し**・時刻なし |

**月表示の予定名は全角5文字以上を読めるようにする。** 実測値（Chromium、
1マス目のチップに全角文字を1字ずつ足し、切れずに収まる最大数）:

| 画面幅 | 1マス | 読める文字数 |
| --- | --- | --- |
| 320px | 44.8px | 6文字（2行） |
| 390px | 54.8px | 8文字（2行） |
| 520px | 73.4px | 12文字（2行） |
| 521px | 73.6px | 6文字（1行） |
| 768px | 108.8px | 9文字 |
| 861px | 122.1px | 6文字（時刻あり） |
| 1180px | 167.7px | 11文字 |
| 1440px | 204.8px | 14文字 |

いずれの幅でも横スクロールは出ない（`scrollWidth` が画面幅と一致）。

**境目の決め方**: 時刻（約34px）を出したままだと 861px を下回ったあたりで
5文字に届かなくなるので、そこで時刻を落としてタイトルに回す。
520px 以下は1行では6文字前後で切れるため、文字を小さくするのではなく
2行に折り返して倍の文字数を出す。
どちらも「時刻より予定名を優先する」という同じ判断による。

## 10. 繰り返し予定の扱い

### 10.1 保存方法

発生を1件ずつ行として保存する方法は取らない。
「毎週月曜、終了日なし」が無限行になるためである。
**1件の予定 + RRULE** で保存し、必要な期間だけ展開する。

ただし**一括インポートで取り込んだ予定は、原則として個別の予定として保存する**。
試合日程のように日付が不規則なものは繰り返しルールで表現できないため。

### 10.2 展開の場所

サーバ側（Route Handler）で展開する。理由は次の2点。

- デスクトップとウェブで展開ロジックが二重化するのを避ける
- 展開の不具合を1か所の修正で直せる

展開には RFC 5545 準拠のライブラリ（`rrule`）を用い、自前実装しない。

### 10.3 タイムゾーンと夏時間

予定は入力時のタイムゾーン（既定 `Asia/Tokyo`）を保持し、そのタイムゾーンで展開する。
日本には夏時間がないため当面は問題にならないが、
UTC 固定で展開すると将来の海外利用時にずれるため、最初からタイムゾーンを持たせる。

### 10.4 例外の考え方

「今週だけ休み」「来週だけ時間変更」は、元の予定を変えずに例外行として記録する。
元の繰り返しルールを保ったまま、個別の回を上書きできる。

| scope | 動作 |
| --- | --- |
| `this` | 対象回の `event_exceptions` を作る（`modified` または `cancelled`） |
| `thisAndFuture` | 元の RRULE に `UNTIL` を設定して打ち切り、対象回以降を新しい予定として作る |
| `all` | 元の予定そのものを更新／削除する |

## 12. 第1弾のスコープ外

- Google カレンダーとの双方向同期（取り込みは行うが、継続同期はしない）
- .ics URL の定期購読
- 本アプリ内部から football-data.org などの外部APIを直接呼ぶこと
- 外部プログラムから自動で書き込むための取込API
  （取り込みは年13回程度であり、自動化する価値がない）
- **取り込み直しによる差分更新**（既存予定の自動更新、手編集の据え置き、
  「ファイルに無い予定」の自動中止）。
  「バッチごと削除して入れ直す」で足りるため作らない。
  覚える操作が増えるだけで、得られるものがない
- 試合結果（スコア）の自動反映
- 家族以外の人との予定調整・招待
- オフラインでの編集と競合解決
- Web Push（ブラウザを閉じている間の通知）
- 予定へのファイル添付
- 多言語対応
