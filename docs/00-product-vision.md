# プロダクト全体像

## 1. 目的

家族の生活情報（予定・お金・食事・続けたいこと）を1か所にまとめ、
「誰かの頭の中にしかない情報」をなくすことを目的とする。

紙のカレンダー、レシート、LINE のやりとりに散らばっている情報を集約し、
家族の誰もが同じ情報を見られる状態をつくる。

## 2. 利用者像

| 利用者 | 主な使い方 | 主に使う端末 |
| --- | --- | --- |
| 家計・予定の主担当 | 入力が多い。まとめて記録し、集計を見る | デスクトップアプリ |
| 配偶者・同居家族 | 参照が中心。外出先で予定を確認し、たまに追加する | ウェブ（スマートフォンブラウザ） |
| 子ども（将来） | 自分の予定の確認 | ウェブ |

想定する家族の人数は 2〜6 人程度。不特定多数向けのサービスではなく、
「自分たち家族が毎日使う道具」として作る。

## 3. ハイブリッド構成の考え方

デスクトップとウェブは **別のアプリではなく、同じアプリの2つの入口** として作る。

- **デスクトップアプリ**: 操作性を最優先する入口。
  キーボード操作、グローバルショートカットによるクイック入力、常駐しての通知、
  まとまった件数の入力といった「腰を据えた作業」を担当する。
- **ウェブアプリ**: 可搬性を最優先する入口。
  スマートフォンのブラウザから予定の確認と簡単な追加ができれば十分とする。

両者で画面・ロジックの実装を共有し、データはサーバ側で一元管理する。
ここが分かれると保守コストが2倍になるため、共通化の維持を設計上の最重要制約とする。

技術としては Next.js + Supabase を採用し、デスクトップは Tauri でそのアプリを包む構成を取る。
詳細は [01-architecture.md](01-architecture.md) を参照。

## 4. 機能スコープ

### 4.1 スケジュール管理（第1弾・本ドキュメント群の対象）

家族の予定を共有カレンダーで管理する。この機能の要点は次の3つ。

- 予定は必ず「誰の予定か」を持ち、人単位で絞り込める
- 外部データを CSV / .ics の取り込みで一括登録できる。
  取り込み1回分は「バッチ」として記録され、まとめて削除して入れ直せる
- デスクトップでもウェブでも同じ操作ができる

詳細は [02-schedule-requirements.md](02-schedule-requirements.md)。

### 4.2 家計簿（第2弾）

- 収入・支出の記録（費目、金額、日付、支払方法、記録者）
- 月次の集計とグラフ、予算と実績の比較
- 固定費（家賃・光熱費・サブスク）の登録
- レシート画像の添付

**続くことを最優先にする。** 家計簿が続かない理由はいつも入力の面倒さで、
集計の細かさは入力が続いた後にしか意味を持たない。

詳細は [07-budget-requirements.md](07-budget-requirements.md)。

### 4.3 献立管理（第3弾・将来）

- 日付ごとの献立登録（カレンダーと同じ日付軸を共有する）
- レシピの登録と、献立からの呼び出し
- 献立から必要な食材を集計した買い物リストの生成
- 買い物リストの購入結果を家計簿の食費として記録する連携

### 4.4 習慣管理（将来）

続けたいことを記録し、続いているかどうかが見える状態にする。

- 習慣の登録（名前、担当するメンバー、頻度、目標）
- 日ごとのチェック。今日やることの一覧
- 連続日数と達成率
- 子どもの歯磨き・宿題、大人の運動や読書といった用途を想定する

家族で使うことに意味がある機能でもある。
自分ひとりで続かないことも、家族に見えていると続きやすい。

#### 習慣は予定ではない

繰り返し予定として実装したくなるが、性質が違う。
ここを混ぜると、カレンダーが未達成の習慣で埋まって使えなくなる。

| | 繰り返し予定 | 習慣 |
| --- | --- | --- |
| 表すもの | その日時に用事がある | その日にやりたいことがある |
| 時刻 | 持つことが多い | 持たないことが多い |
| 実施の記録 | 残らない | **残すこと自体が目的** |
| やらなかったとき | 予定が過ぎるだけ | 「できなかった」という情報になる |
| カレンダー表示 | 必ず出す | 出しすぎると邪魔になる |

そのため予定とは別のデータとして持つ。
カレンダーに出すかどうかは習慣ごとに選べるようにし、既定では出さない。

#### 繰り返しの仕組みは共用する

「平日だけ」「週3回」といった頻度の指定は、
スケジュール管理で作る繰り返し予定（RRULE の展開）と同じ仕組みで足りる。

このため **繰り返しの展開ロジックは予定に結び付けず、
「ルールと期間を渡すと日付の一覧が返る」独立した部品として作る**。
スケジュール管理の実装時点でこれを意識しておけば、
習慣管理では画面と記録だけを作ればよくなる。

#### 見えることの扱い

記録が家族に見えるのは後押しになるが、見張られている感じにもなる。
公開範囲（自分だけ／家族に見える）を習慣ごとに選べるようにする。

### 4.5 機能間の関係

4機能は独立したアプリではなく、
**日付と家族メンバーを共通の軸として連携する**ことに価値がある。

```
            日付 ・ 家族メンバー ・ 認可（RLS）
          スケジュール管理の段階で作る共通の土台
                          │
      ┌──────────┬────────┴────────┬──────────┐
      │          │                 │          │
┌─────▼─────┐ ┌──▼───┐        ┌────▼───┐ ┌────▼────┐
│ スケジュール │ │ 習慣  │        │  献立   │ │  家計簿  │
└───────────┘ └──────┘        └────┬───┘ └────▲────┘
                                    │          │
                                    └──────────┘
                                買い物リスト → 食費として記録
```

このため、スケジュール管理の段階で
「家族」「メンバー」「日付・タイムゾーンの扱い」「認可」といった土台を、
後続機能でも使える形で作っておく。

## 5. 明確にスコープ外とするもの

- 他人（家族外）との予定調整、招待状の送受信
- 銀行口座・クレジットカードとの自動連携
- 確定申告・税務向けの機能
- 家族以外への一般公開、マルチテナントのSaaS化

## 6. 成功の基準

第1弾（スケジュール管理）としては次を満たせれば成功とする。

1. 紙のカレンダーを見なくても、家族の予定が把握できる状態になる
2. 予定の追加が、紙に書くより速いと感じられる（デスクトップで概ね10秒以内）
3. 外出先でスマートフォンから予定を確認できる
