# 画面の骨組み

スケジュール管理は4機能のうちの1つでしかない。
習慣・家計簿・献立が入ったときに画面がどう並ぶかを、先に決めておく。

試作: [prototypes/shell.html](prototypes/shell.html)

## 1. 決めたこと

| | 決めたこと |
| --- | --- |
| 機能の切り替え | **パソコンは上のタブ、スマートフォンは下のバー** |
| 機能の中の切り替え | その下の細いタブ（2段目） |
| 機能の数 | 最大5つ（4機能＋設定）。これ以上増やさない |
| 作っていない機能 | メニューに出さない |
| 左の縦メニュー | **作らない** |

## 2. なぜ左に縦のメニューを置かないか

カレンダーは横幅がそのまま「予定名の読める文字数」になる。
1マスの幅はほぼ「画面幅 ÷ 7」で、左に 200px のメニューを置くと
1マスが 28px 狭くなる。実測では2〜3文字ぶんに当たる
（[02-schedule-requirements.md](02-schedule-requirements.md) 9.5）。

行き先が5つしか無いのに、常時その幅を明け渡す理由がない。
上のタブなら横幅を1pxも使わない。

家計簿や献立のように表を並べる機能が増えても、
横幅は広いほうが都合がよく、この判断は変わらない。

## 3. なぜスマートフォンは下なのか

片手で持ったとき、画面の上端は指が届きにくい。
機能の切り替えは毎日何度も押すので、下に置く。

上のバーには機能名と家族・自分だけを残す。

## 4. 2段のナビゲーション

```
┌──────────────────────────────────────────────┐
│ MeManager  スケジュール 習慣 家計簿 献立  設定  │ ← 機能（1段目）
├──────────────────────────────────────────────┤
│ カレンダー  取り込み履歴                        │ ← 機能の中（2段目）
├──────────────────────────────────────────────┤
│                                              │
│                  画面の中身                    │
```

2段目は機能ごとに中身が変わる。

| 機能 | 2段目 |
| --- | --- |
| スケジュール | カレンダー / 取り込み履歴 |
| 習慣 | 今日 / 記録 |
| 家計簿 | 入力 / 一覧 / 集計 / 予算 |
| 献立 | 献立 / レシピ / 買い物 |
| 設定 | メンバー / 家族 / 表示 |

**2段目が1つしか無い機能では、2段目を出さない。**
いまのスケジュール管理がこれに当たる。

## 5. URL

機能ごとに区切る。あとから増やすときに迷わないようにするため。

| 機能 | URL |
| --- | --- |
| スケジュール | `/schedule` |
| 習慣 | `/habits` |
| 家計簿 | `/budget` |
| 献立 | `/meals` |
| 設定 | `/settings`（メンバーは `/settings/members`） |

現状の `/calendar` と `/members` はこの形に移す。
**移すなら今のうちにやる。** 使い始めてからだと、
ブックマークや家族に伝えたURLが変わって面倒になる。

## 6. 機能の登録は1か所にまとめる

メニューは、機能の一覧を持つ1つのファイルから作る。

```ts
// apps/web/src/lib/nav/features.ts（予定）
export const FEATURES = [
  { id: "schedule", label: "スケジュール", href: "/schedule", icon: …, ready: true,
    screens: [{ label: "カレンダー", href: "/schedule" }] },
  // 習慣・家計簿・献立は、作ったときにここへ足す
];
```

上のタブ・下のバー・2段目のタブは、すべてこの一覧から作る。
**新しい機能を足す作業は、この配列に1行足すことになる。**
ナビゲーションの実装を機能ごとに書かない。

`ready: false` の機能はメニューに出さない。
押しても何も起きないタブが並ぶと、壊れているように見えるため。

## 7. いつ作るか

**機能が1つの間は、タブもバーも出さない。**
行き先が1つしか無いのにタブを出しても意味がない。

ただし次の2つは、機能が1つのうちに済ませておく。

1. **URL の整理**（5節）— あとからだと面倒になる
2. **機能の一覧と、それを読むシェルの実装**（6節）— 2つ目の機能を作るときに
   ナビゲーションの設計から始めなくて済む

2つ目の機能（習慣管理）を作る時点で、タブと下のバーを表に出す。
