# 外部データのフィード同期

対象: [02-schedule-requirements.md](02-schedule-requirements.md) 4.7.2「フィード同期」の詳細仕様
最初の利用先: football-data.org から取得したサッカーの試合日程

---

## 1. 位置づけ

外部サービスのデータを MeManager の予定として継続的に反映するための仕組み。

MeManager 本体は **外部サービスを直接呼ばない**。
外部サービスごとの差異（認証方式、レート制限、レスポンス構造、利用規約）を本体に持ち込むと、
データ源が増えるたびに本体の改修が必要になるためである。

代わりに、次の役割分担にする。

```
┌──────────────────┐   ①取得   ┌──────────────────┐
│ football-data.org │ ────────▶ │  変換プログラム    │
└──────────────────┘           │  （別途作成）      │
                               └─────────┬────────┘
                                         │ ②本アプリの JSON 形式に変換して送信
                                         ▼
                               ┌──────────────────┐
                               │  MeManager        │
                               │  取込API          │
                               └──────────────────┘
```

変換プログラムは MeManager のリポジトリ外にあってもよい。
本書が定めるのは **②の契約（JSON の形式と同期の意味論）** であり、
これさえ守れば、データ源が football-data.org 以外に変わっても本体は無改修で済む。

## 2. 設計方針

### 2.1 CSV ではなく JSON にする

当初は CSV を想定していたが、送り手が人ではなくプログラムであるなら CSV を経由する理由がない。

| | CSV | JSON（採用） |
| --- | --- | --- |
| 文字コード | Shift_JIS などの判定が要る | UTF-8 固定 |
| 型 | すべて文字列。日時の解釈が曖昧 | 日時・真偽値・配列をそのまま表現できる |
| 構造 | 1行1予定。担当者の複数指定が書きにくい | 入れ子で素直に書ける |
| 外部キー | 列を決めて運用で守るしかない | 形式の一部として必須にできる |

人が手元のファイルを入れる経路（.ics / CSV）は別に残す。そちらは今も必要。

### 2.2 「1回入れて終わり」にしない

サッカーの試合日程は、登録したあとに内容が変わる。

- 日程だけ決まっていた試合の、キックオフ時刻が後から確定する
- 悪天候や日程変更で延期・中止になる
- 放送の都合でキックオフ時刻がずれる

そのため、取込は「毎回まっさらに入れ直す」でも「1回だけ入れる」でもなく、
**外部キーで既存の予定と照合して更新する（upsert）** 形にする。

全消し・全入れ直しにしない理由は、予定のIDが毎回変わってしまい、
メモや通知の設定、家族が付けた変更がすべて失われるため。

### 2.3 消えたものをどう扱うか

外部データから試合が消えることがある。このとき「送られてこなかったから消す」と単純に判断すると、
9月分だけを送ったつもりが10月以降の予定まで消える事故が起きる。

そこで、**リクエストに対象期間（`window`）の宣言を必須にする**。
削除・中止の判断は、宣言された期間の中だけで行う。

さらに、消えた予定は削除せず **「中止」として残す**。
予定表としては、黙って消えるより「中止」と分かるほうが役に立つ。

## 3. フィードの登録と認証

### 3.1 フィード

同期の単位。画面から登録する。

| 設定項目 | 説明 |
| --- | --- |
| 名称 | 例: 「プレミアリーグ 2026-27」 |
| 取込先カレンダー | 例: 「サッカー」 |
| 既定の担当者 | 1人以上必須。このフィードで作られる予定の担当者になる |
| 手編集の上書き | 既定オフ（人が編集した予定は同期で上書きしない） |
| 有効／停止 | 停止中は同期を受け付けない |

コンペティションごとにフィードを分けることを勧める。
「プレミアリーグは父、チャンピオンズリーグは父と子」のように担当者を変えられ、
カレンダーの表示・非表示も別々に切り替えられる。

### 3.2 取込トークン

フィードの登録時に専用トークンを発行する。

- 形式: `mmf_` + 32バイトの乱数（Base64URL）
- 保存: ハッシュのみを保存し、平文は発行直後に一度だけ表示する
- 権限: **そのフィードへの同期のみ**。他のフィード、他のテーブルには一切触れない
- 失効・再発行ができる

**Supabase のサービスロールキーを変換プログラムに渡してはならない。**
サービスロールキーは RLS を迂回し、将来の家計簿を含む全データを操作できる。
変換プログラムは自分のPCや CI 上で動き、鍵が漏れる経路が本体より多いため、
権限を絞った別のトークンを使う。

### 3.3 認証方法

```
POST /api/feeds/{feedId}/sync
Authorization: Bearer mmf_xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx
Content-Type: application/json
```

サーバはトークンのハッシュからフィードを解決し、
そのフィードの `family_id` と `calendar_id` に閉じた操作だけを行う。
リクエストのどこにも家族IDやカレンダーIDを書かせない（書けてしまうと越境の余地が生まれる）。

## 4. 取込API

### 4.1 リクエスト

```json
{
  "window": {
    "from": "2026-09-01T00:00:00Z",
    "to":   "2026-11-01T00:00:00Z"
  },
  "missingPolicy": "cancel",
  "events": [
    {
      "externalKey": "football-data:match:497181",
      "title": "アーセナル vs リヴァプール",
      "startsAt": "2026-09-19T14:00:00Z",
      "endsAt":   "2026-09-19T16:00:00Z",
      "allDay": false,
      "timezone": "Asia/Tokyo",
      "status": "confirmed",
      "location": "Emirates Stadium",
      "description": "プレミアリーグ 第5節",
      "externalUpdatedAt": "2026-09-12T00:20:31Z"
    }
  ]
}
```

#### window（必須）

削除・中止の判断を行う範囲。`from` 以上 `to` 未満。
この範囲の外にある予定は、このリクエストでは一切変更されない。

最大範囲は 400日。`from` と `to` の両方が必須で、片方だけの指定はエラーにする。

#### missingPolicy（任意、既定 `cancel`）

`window` の中に既存の予定があるのに、`events` に含まれていなかった場合の扱い。

| 値 | 動作 |
| --- | --- |
| `cancel`（既定） | 状態を「中止」にする。予定は残る |
| `delete` | 論理削除する |
| `ignore` | 何もしない（部分的な更新だけを送りたいとき） |

部分更新を送るときは `ignore` を指定する。既定を `cancel` にしているのは、
「全件送る」が本来の使い方であり、そのときに消えた試合を拾えるようにするため。

#### events（必須、最大1,000件）

| フィールド | 必須 | 型 | 説明 |
| --- | --- | --- | --- |
| `externalKey` | ○ | string(255) | 外部側の識別子。フィード内で一意 |
| `title` | ○ | string(200) | |
| `startsAt` | △ | ISO 8601 | 時刻付き予定のとき必須。タイムゾーン付きで送る |
| `endsAt` | △ | ISO 8601 | 同上。`startsAt` 以降であること |
| `startDate` | △ | `YYYY-MM-DD` | 終日予定のとき必須 |
| `endDate` | △ | `YYYY-MM-DD` | 同上。その日を含む |
| `allDay` | ○ | boolean | true なら `startDate`/`endDate`、false なら `startsAt`/`endsAt` を使う |
| `timezone` | | string | IANA 名。既定 `Asia/Tokyo` |
| `status` | | string | `confirmed` / `tentative` / `cancelled`。既定 `confirmed` |
| `location` | | string(200) | |
| `description` | | string(2000) | |
| `color` | | string | `#RRGGBB`。未指定ならカレンダー／担当者の色 |
| `assigneeMemberIds` | | uuid[] | 指定するとフィードの既定担当者を上書きする |
| `externalUpdatedAt` | | ISO 8601 | 外部側の最終更新日時。差分判定に使う |

`allDay` と日時フィールドの組み合わせが合わない行はエラーとして弾き、
その行だけをスキップして残りは処理する（1行の不備で全体を落とさない）。

### 4.2 レスポンス

```json
{
  "runId": "0f3c8b2e-...",
  "window": { "from": "2026-09-01T00:00:00Z", "to": "2026-11-01T00:00:00Z" },
  "received": 58,
  "created": 12,
  "updated": 3,
  "cancelled": 1,
  "skippedLocallyModified": 2,
  "unchanged": 40,
  "failed": 0,
  "warnings": [
    {
      "externalKey": "football-data:match:497203",
      "message": "手編集された予定のため更新しませんでした"
    }
  ]
}
```

`unchanged` を返すのは、同期が正しく冪等に動いていることを呼び出し側から確認できるようにするため。
2回目以降の同期で `created` が増え続けるなら、外部キーの生成に問題がある。

### 4.3 エラー

| HTTP | code | 意味 |
| --- | --- | --- |
| 401 | `invalid_token` | トークンが不正、または失効している |
| 403 | `feed_inactive` | フィードが停止中 |
| 400 | `invalid_window` | `window` が欠けている、範囲が400日を超える |
| 400 | `too_many_events` | 1,000件を超えている |
| 409 | `sync_in_progress` | 同じフィードの同期が実行中 |
| 422 | `no_assignee` | 担当者が解決できない（既定担当者が空） |

429（レート制限）は、同一フィードに対して毎分6回を超えたときに返す。

## 5. サーバ側の処理手順

```
1. トークンを検証し、フィードを特定する
2. フィードが有効か確認する
3. window と events を検証する（不正な行は failed として記録し、以降の処理から外す）
4. window 内の既存予定を、feed_id で取得する
5. events を1件ずつ処理する
     externalKey が既存にない       → 作成（created）
     既存にあり、内容が同じ          → 何もしない（unchanged）
     既存にあり、locally_modified    → 何もしない（skippedLocallyModified）
        ※ フィードの overwrite_local_edits が true なら更新する
     既存にあり、内容が違う          → 更新（updated）
6. window 内の既存予定のうち、今回の events に含まれなかったものを
   missingPolicy に従って処理する（cancelled / deleted / 何もしない）
7. feed_sync_runs に結果を記録し、フィードの last_synced_at を更新する
```

処理全体を1トランザクションで行う。途中で失敗したら何も変更せず、
`feed_sync_runs` に失敗として記録する。中途半端に反映された状態を作らない。

「内容が同じ」の判定は、`externalUpdatedAt` があればそれを優先し、
なければ比較対象フィールドを突き合わせる。

## 6. football-data.org からの変換

変換プログラム側の実装指針。MeManager 本体の仕様ではないが、
契約を満たすために必要な事項をここにまとめる。

### 6.1 API の概要

| 項目 | 内容 |
| --- | --- |
| ベースURL | `https://api.football-data.org/v4` |
| 認証 | `X-Auth-Token` ヘッダにトークン |
| 試合の取得 | `GET /v4/competitions/{code}/matches?dateFrom=&dateTo=` |
| レート制限 | 無料プランで 10リクエスト/分 |
| 無料プランの対象 | プレミアリーグ、ラ・リーガ、ブンデスリーガ、セリエA、リーグアン、エールディヴィジ、プリメイラ・リーガ、チャンピオンズリーグ、ブラジル全国選手権、チャンピオンシップ、ワールドカップ、欧州選手権 |

**J リーグおよび国内アマチュアの試合は無料プランに含まれない。**
子どもが実際にプレーする試合の日程は、この経路では取得できない。
それらはファイル取込（.ics / CSV）で登録する。

### 6.2 マッピング

| football-data.org | MeManager | 変換 |
| --- | --- | --- |
| `id` | `externalKey` | `football-data:match:{id}` |
| `utcDate` | `startsAt` | そのまま（UTC）。JST への変換は MeManager 側が行う |
| — | `endsAt` | `startsAt` + 所要時間（6.4 参照） |
| `status` | `status` | 6.3 の対応表 |
| `homeTeam.shortName` / `awayTeam.shortName` | `title` | `{home} vs {away}` |
| `competition.name` + `matchday` | `description` | 例: 「プレミアリーグ 第5節」 |
| `stage` / `group` | `description` | ノックアウト時は「決勝トーナメント 準々決勝」など |
| `venue` | `location` | 提供されないことがある。無ければ省略 |
| `lastUpdated` | `externalUpdatedAt` | そのまま |
| `score` | — | **既定では送らない**（6.5 参照） |

`shortName` は `name`（`Arsenal FC`）より短く表示に向く。
日本語表示にしたい場合は、変換プログラム側にチーム名の対応表を持つ。
MeManager 側はチーム名を解釈しないので、どちらでも動く。

### 6.3 状態の対応

| football-data.org の status | MeManager の status | 備考 |
| --- | --- | --- |
| `SCHEDULED` | `tentative` または `confirmed` | 6.4 の判定による |
| `TIMED` | `confirmed` | 日時が確定した状態 |
| `IN_PLAY` / `PAUSED` | `confirmed` | |
| `FINISHED` | `confirmed` | |
| `AWARDED` | `confirmed` | |
| `POSTPONED` | `cancelled` | タイトルの末尾に「（延期）」を付ける |
| `SUSPENDED` | `cancelled` | 「（中断）」 |
| `CANCELLED` | `cancelled` | 「（中止）」 |

### 6.4 キックオフ時刻が未確定の試合

これが実装で最も間違えやすい箇所。

日程だけが決まっていてキックオフ時刻が未定の試合は、
`utcDate` に仮の時刻（多くは `00:00:00Z`）が入る。
これをそのまま時刻付きの予定として登録すると、
日本時間では **朝9時の予定** として表示され、誤った情報になる。

変換プログラムは次のように判定する。

```
utcDate の時刻部分が 00:00:00Z、かつ status が SCHEDULED
  → 終日予定として送る（allDay: true, startDate: JST での日付, status: "tentative"）
それ以外
  → 時刻付きの予定として送る（allDay: false, status: "confirmed"）
```

時刻が確定すると、次の同期で同じ `externalKey` のまま時刻付きの予定に更新される。
`allDay` の切り替えも更新として扱えるよう、取込API側で対応しておく。

なお、`status` の運用は提供側の都合で変わることがある（`TIMED` を使わなくなった時期がある）。
状態名だけに依存せず、**時刻が入っているかどうかで判断する**ほうが壊れにくい。

### 6.5 時差とスコアの扱い

**時差**: 欧州の試合は日本時間で深夜から早朝になる。
21:00 UTC の試合は翌日の 06:00 JST であり、日付が変わる。
`startsAt` を UTC のまま送れば MeManager 側が正しく変換するので、
変換プログラムで日本時間に直そうとしないこと。

**スコア**: `score` を `description` や `title` に入れると、
録画で観る家族にとって結果が見えてしまう。既定では送らない。
入れたい場合は、変換プログラム側のオプションとする。

### 6.6 変換プログラムの推奨動作

| 項目 | 推奨 |
| --- | --- |
| 実行頻度 | 1日1回で足りる。日程変更が多い時期は1日数回 |
| 取得範囲 | 今日から90日先まで |
| `window` | 取得範囲と一致させる（ずれると意図しない中止が発生する） |
| `missingPolicy` | `cancel` |
| レート制限 | 10リクエスト/分。コンペティションごとに間隔を空ける |
| 失敗時 | 取得に失敗したコンペティションの分は送らない（部分的な送信で `cancel` されるのを避ける） |

最後の項目が重要。
football-data.org の取得に失敗したまま空の `events` を送ると、
その期間の試合がすべて中止扱いになる。
**取得に失敗したら同期そのものを中止する**こと。

### 6.7 利用条件

- 無料プランの利用範囲を超えないこと（レート制限の遵守）
- 取得したデータを第三者に再配布しないこと。本アプリは家族内での利用に閉じている
- 表示にあたって出典の明示が求められる場合は、フィードの説明欄にその旨を記載する

## 7. 動作確認の項目

実装後、次を確認する。

| # | 確認内容 | 期待する結果 |
| --- | --- | --- |
| 1 | 同じデータを2回送る | 2回目は `created: 0`、件数が増えない |
| 2 | キックオフ時刻を変えて送る | `updated: 1`、予定の時刻が変わる |
| 3 | 1件を除いて送る（`missingPolicy: cancel`） | その1件が「中止」になり、残りは変わらない |
| 4 | `window` の外に予定を作ってから同期する | その予定は変更されない |
| 5 | 予定にメモを追記してから同期する | メモが残り、`skippedLocallyModified` に数えられる |
| 6 | `status: tentative` の終日予定を、時刻付き `confirmed` で送り直す | 同じ予定が時刻付きに変わる |
| 7 | 空の `events` と `missingPolicy: cancel` を送る | `window` 内が全部中止になる（この挙動を理解したうえで運用する） |
| 8 | 別フィードのトークンで呼ぶ | 401 または 403 になり、データが変わらない |
| 9 | 1,001件を送る | 400 `too_many_events` になり、1件も登録されない |

7番は事故そのものに見えるが、仕様としては正しい動作である。
だからこそ 6.6 の「取得に失敗したら送らない」が要る。
